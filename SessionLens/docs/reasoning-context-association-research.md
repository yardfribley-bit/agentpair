# 几轮上下文与 reasoning 如何关联需求

研究日期：2026-10-06。检查范围为 SessionLens 当前代码、本机 collector.db 的只读查询和一个 WorkBuddy 会话的结构抽样。本次没有向模型发送真实会话，也没有修改产品的关联行为。

## 结论

可以利用几轮上下文和已记录的 reasoning 帮助关联需求。应先用原始消息关系还原执行往返，再用用户原话、Agent 方案、修改和确认理解需求。reasoning 解释的是 Agent 当时如何理解和决定，不等于用户已经授权，也不证明工具执行成功。

需要分别回答两个问题：

1. 这些消息、思路、工具和返回在日志中如何相接？这是结构关系。
2. 这些动作是在完成哪个需求、哪个版本？这是需求归属，可能需要语义判断。

## 本机数据发现

当前 task_steps 派生索引中，WorkBuddy 有 13,654 条 reasoning 记录，其中 13,587 条有非空文本；Codex 有 29,594 条，其中 1,152 条有非空文本。这是检查时的索引计数，不代表独立模型轮次数、原始采集完整率或全部思考都可读取。

检查的 WorkBuddy reasoning 原始记录包含 id、parentId、sessionId，以及 providerData 内的 conversationRequestId、traceId、messageId。本次抽查的记录还有 rawContent 中的 reasoning_text。采集器保留了这些原始字段，当前任务关联层却没有用它们建立消息父子关系。

抽查 WorkBuddy 会话 fb117c98-3a4f-4632-8779-e26e3b50271a 的 908 条已索引步骤，包含 16 条用户提问、164 条 reasoning、120 条 Agent 回复，以及工具调用和返回各 304 条。907 条步骤带 parentId，其中 905 条父节点在这批步骤内能解析，均指向更早记录；另外两条未在本批已索引步骤内解析，不据此判断漏采。

直接观察到的父子关系包括：

- 16 条 reasoning 的父节点是用户提问。
- 181 条工具调用的父节点是 reasoning；另有 123 条父节点是工具返回。
- 287 条工具返回的父节点是工具调用；另有 17 条父节点是其他工具返回。
- 148 条 reasoning 的父节点是工具返回。

这些关系说明它不是固定的“一段思路配一个工具”结构。并行调用、连续返回、基于返回继续调用，都需要允许。工具调用与返回仍应核对 callId；不能只看父节点类型。

该样本有 13 组非空 conversationRequestId，均同时出现 reasoning 和工具调用。这些编号可以辅助分组，但字段的完整产品语义尚未验证，不能直接等同于用户需求编号。

## 一个真实承接例子

用户只说“继续”。随后 WorkBuddy 的 reasoning 明确记录：它把这句话理解为继续做“记忆面内容查看与 diff”，接着做“风险收敛工作台”。随后出现 Bash 调用，读取相关工程文件。

该 reasoning 的 parentId 指向这条用户提问；随后前两个工具调用的 parentId 指向该 reasoning，并具有相同的请求编号和 traceId。

所以可以表达为：“用户说继续 → Agent 理解为推进记忆查看与差异对比 → 调用命令查看相关代码”。但最终需求归属还应核对此前用户要求和 Agent 方案；reasoning 中自行补充的默认选择，必须标成 Agent 的决定，不能写成用户批准。

Codex 的一个“继续”样本则只有两条短摘要，内容是准备设备登录卡片、添加 Android 交接说明；原始记录同时带 encrypted_content。本研究未解密该字段。该样本可用于辅助判断主题，但不能当作完整思考过程。没有可读 reasoning 时，系统仍要依靠用户讨论、Agent 回复、工具参数与返回关联。

## 当前代码的缺口

- semantic_lineage.context_for_task 读取有限前后轮次，但每轮只提供用户正文与最后一条 Agent 回复；没有提供 reasoning、消息父子关系和请求分组。
- task_presentation.project 把一段 reasoning 与后面遇到的第一个工具配成回放片段。它会在新用户消息处停止，也使用 callId 找返回，但 reasoning 到工具的连线仍是先后顺序推测，没有验证 parentId。
- 一段 reasoning 后连续调用多个工具时，现有回放只给这段思路配第一个工具。
- 原始记录已经保留结构字段，因此部分改进是补关联投影，不需要重新采集全部历史。

## 建议的关联方式

第一步，在同一来源、同一会话内索引源消息 id、parentId、callId、请求编号和 traceId。保留原始事件引用。检查重复源编号、缺失父节点、循环、分支和不符合顺序的边；不能跨来源或会话碰巧同号就关联。源字段完整时优先用它们；缺失时才使用顺序候选，并明确标注。

第二步，围绕相关用户轮次选取有限讨论：原始需求、Agent 提议、用户的修改与确认、相关 reasoning、工具名称和关键参数。窗口不按“固定几轮就是一个需求”划分；发现承接指代或未解决引用时，在预算内回查前置方案，预算不足则保留缺口。上下文压缩摘要仅作定位线索，能找到原话时引用原话。

第三步，分别判断“用户要求什么”“Agent 理解成什么”“实际工具做了什么”。目标、约束、产物或指代承接支持语义关联；仅主题词相似、时间接近、父消息连续、Agent 声称用户同意，都不能独立确定需求。用户新要求不能被 reasoning 覆盖。

第四步，每次工具执行关联当时有效的需求和修改版本，并保留支持证据。后来的补充要求不倒推为此前执行依据。用户插入新任务后恢复旧任务，可以关联早期需求，但必须有内容依据。

第五步，用户看到简短解释，例如：“这次写代码承接了你前面确定的手机号登录方案；Agent 先说明改动，再调用写文件工具。点击可查看原话和调用参数。”缺少确认或只是顺序候选时，也用普通语言说明。

## 关联可信度要分别呈现

- 原始日志关系：按源消息父编号、调用编号等建立；说明日志记录的关系，不推断全部因果。
- 需求语义判断：引用用户要求、方案讨论和已记录 reasoning；属于可纠正的推断。
- 用户修正：本机人工指定归属，覆盖模型推断，保留原始记录。
- 未确定：前文缺失、多个可能方案或证据矛盾，提示补充或选择，不强行合并。

SessionLens 的日志上下文不能直接当作实际发给大模型的完整请求。项目记忆、系统提示词、检索结果等是否进入具体网络请求，需结合 AppLens 捕获的请求证据核对，不能因为 reasoning 提到了某项信息就认定已上传。

## 后续验收重点

使用“原始需求→多轮讨论→不同措辞确认→执行”的真实样本，检查方案选择、约束修改、插入其他任务后恢复、并行工具、迟到返回、摘要压缩、reasoning 缺失及 Agent 理解错误。比较只用对话、加入结构关系、再加入 reasoning 的结果，衡量误合并、误拆分、版本绑定和无法判断的情况；不要仅凭一两个成功样本宣称完成。
