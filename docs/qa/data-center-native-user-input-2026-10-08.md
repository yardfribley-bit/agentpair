# 用户输入缺失修复验收

## 已复现的问题

2026-10-08 用户在 `tool="exec"` 搜索反馈用户输入缺失。TinyFish 运行 运行标识保留本机 只读实测前五条中两条显示“未找到对应用户输入”，另两条只有“。”；详情仍能看到旧的候选提问。不是单纯 CSS 隐藏。

服务器原文证据说明：

- Codex `payload.internal_chat_message_metadata_passthrough.turn_id` 已采集，但数据中心只取直接 `turn_id/turnId`，导致原生关联丢失。
- 空白调用来自子 Agent 会话；其用户记录主要是创建时继承的历史，距离当前调用超过旧候选窗口 2 小时。当前任务来自主 Agent 分派，不能把继承的旧提问当新任务。
- 子会话 `turn_started/turn_context` 原文有 `root_turn_id`，`session_metadata` 有 `parent_thread_id`；主会话真实用户消息的原生轮次与 root 一致。可以据明确关系恢复原输入，无需按时间跨会话猜测。
- 短确认旧逻辑不一致：“做”会被过滤，“。”却通过空字符串判断而成为需求标题。

## 修复范围

- 类型安全提取已知元字段中的 turn/root-turn，保留来源路径；不同 ID 冲突时标记未知，不任取一个。
- 同设备、账号、来源内沿显式父会话链，使用 root-turn 查唯一主会话输入；控制消息不计作用户提问。父链最多 8 层，重复、循环、缺失、冲突均停止。
- 明确关联的“做”“。”“补齐”等保留本轮输入，前序完整提问另列候选线索，不能自动宣称为同一业务任务。
- 列表、需求分组和详情保持相同用户锚点，子 Agent 与主 Agent 依据同一原文输入归组。冲突可在详情查看，返回不能覆盖其调用的冲突状态。
- 历史元信息增量回填，原始采集正文、索引文本和上传水位不重建、不删除。大于 4 MB 且未在现有投影中的旧源记录标记本次迁移不可用，不无界解析。
