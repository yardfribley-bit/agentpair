## 待修复问题

| 优先级 | 问题 | 证据与复现 | 用户影响 |
| --- | --- | --- | --- |
| P1 | 一个会话的待确认请求阻止另一会话提问 | 前端隔离执行真实 submit 处理函数：pendingReply 属于 A，current 为 B，提交后 API 调用次数为 0，提示上一条问题等待确认。renderPending 又只在 A 展示状态。 | 用户切换到 B 仍无法提问，且当前会话看不到解除阻塞的入口。 |
| P1 | 发送没有超时与等待升级机制 | 代码检查：api 使用 fetch，没有超时、AbortController 或限时状态核查；submit 等待这个 Promise。未模拟实际网络黑洞。 | 请求一直挂起时，可能长期停在“正在发送”，没有明确下一步。 |
| P1 | 新建任务触及固定总量上限 | 线上列表已有 20 个任务；tasks.py 在总任务数 >=20 时拒绝 create。此前 409 记录与此一致，本次未再次创建任务。 | 用户无法发起新需求；历史任务永久占用额度。应设计可解释的配额/归档机制，不能直接去掉资源保护。 |
| P2 | 新建任务提交缺少防重复与即时反馈 | create-form 处理函数 await 请求前没有禁用按钮或插入提交状态；代码检查。 | 慢网下重复点击可能重复提交，用户难以判断是否收到。 |
| P2 | 轮询没有防重入 | 每 2 秒 refresh，函数串行请求列表及当前任务，没有 in-flight 锁；代码检查，未做压力测试。 | 接口慢于周期时会叠加请求，增加小规格服务器负担。 |

## 验收建议

先处理 P1：跨会话待确认状态隔离；发送后即时显示问题；超时后核查是否已受理，避免盲目重发；新任务上限给出可操作说明。随后在真实浏览器验证发送、断网、恢复、切换任务、追问、滚动阅读时收到新回复，以及输入框是否遮挡结果。

本次未修改产品代码、未部署修复。自动测试通过不能替代以上交互验收。
