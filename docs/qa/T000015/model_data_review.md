# 数据中心（/model-data）专项审核：性能根因、SessionLens / AppLens 数据链路与改版方案

- 审核员：Grok Bot · 2026-10-20 18:55–19:40 UTC
- 范围：
  - 页面：`https://www.chuhaijian.com/model-data`、`/model-data/rankings`、`/model-data/raw`
  - 代码：仓库 `codex/agentpair-mvp@58b55de`
- 方法：
  - 只读匿名探测：逐个接口计时、测量体积、做并发测试（最多同时 3 个请求）。
  - 无头浏览器分别以桌面 1440 和手机 390 宽度渲染页面。
  - 通读前后端代码。
  - 线上数据只记录数量和结构，不引用内容。
- 说明：按站方意见，匿名公开属于展示设计，本报告不作为缺陷处理。附带一条建议：展示用数据最好换成自有或已脱敏的数据，因为现在的数据里有第三方设备名、上传账号、提示词原文（见第 7 节）。

## 0. 一句话结论

数据中心**现在完全不可用**：
- 首页搜索和使用排行，无论怎么筛选，都在约 **12.1 秒**后返回 409「搜索超过处理时限」。
- 有并发请求时，后来的请求约 **2.1 秒**就返回同样的 409。

根因有四层，都不是筛选条件能缓解的，而是**每次请求都在一把全局锁里重做全量工作**：
1. 每次请求先做增量同步；
2. 在全量记录上做去重计数、来源分组和多次 DISTINCT；
3. 关键词匹配用 Python 函数逐行扫描大文本；
4. AppLens 每次请求都存一份完整历史上下文，数据量按平方级增长。

另外，SessionLens 和 AppLens 两类数据在同一个结果列表里**混排，也不跨来源去重**。同一段用户提问会以多份副本出现，命名和口径也不一致。

## 2. 根因（附代码位置）

### R1 每个请求都在全局锁里做与筛选无关的全量计算（最主要）

`DataCenter.search()`（`agentpair/data_center.py:1111-1168`）和 `capabilities()`（`:1170-`）对**每次请求**都按下面的顺序执行：

1. `with self.lock`（`:1116`、`:1176`）：这把锁是按数据库文件全局共享的 `RLock`（`:686-687`），所有搜索、排行、详情请求都要排队。
2. `self._sync(db)`（`:1117`、`:1177`、`:1650`、`:1832`）：
   - 每次都对两张源表做 `count(*)`（`:793` 的 `session_events`，`:806` 的 `applens_model_context`）。
   - 增量写入索引，**写入发生在读请求里**。
   - 设备别名有变化时，会删掉全部 AppLens 记录再重建（`:812-814`）。
3. `_scope()`（`:732-742`）：每次请求都去设备库读全部设备，建临时表。
4. `_query_scope()` 先在**全量范围**上执行一次 `count(*)`（`:1021`）。条件里带 `DUPLICATES`（`:45-48`），这是一个相关子查询，对每一行都要 `json_extract(metadata,'$.recordDigest')`。
5. 把匹配结果写入临时表 `dc_matches`（`:1121-1122`），然后再做两次计数。
6. 拿到当前页之后，还有一串**和当前页无关**的全量统计：
   - `sources` 再跑一遍带 `DUPLICATES` 的分组统计（`:1151`）；
   - `_facets` 跑三次全量 DISTINCT（`:1026-1029`）；
   - `excludedUnavailableRecords` 和 `duplicateAliasRecords` 各做一次全表计数（`:1162-1163`）；
   - 还要计算 `capabilityRemaining`。

**对应测量结果**：`pageSize=1`、单设备、24 小时窗口全都是 12.1 秒，说明耗时就在第 2、4、6 步这些固定开销上。

### R2 关键词搜索没有全文索引，用 Python 函数逐行扫大文本

- `_term_sql()` 的关键词、IP、域名匹配，写法是 `EXISTS(SELECT 1 FROM dc_fields f WHERE f.record=r.key AND dc_match(f.value,?,?))`（`:950-956`）。
- `dc_match` 是注册给 SQLite 的 Python 函数（`:722-724`），内部做 `casefold()` 加子串查找，或正则匹配（`:196-206`）。
- 这种写法用不上任何索引，每条记录的每个字段都要从 SQLite 传到 Python 再处理。

### R3 AppLens 数据呈平方级膨胀，并且在索引里存了两遍

- 写入时 `_app_projection()`（`:647-676`）先把完整请求正文存成一个 `context` 字段，又把正文里的每条消息拆开，**再存一遍**到 user / reply / result / arguments 字段。
- WorkBuddy 每次请求都携带完整历史，所以第 N 次请求要把前 N−1 轮的内容全部重复存一次。实测平均每次请求 290 KB，同一段 SOUL.md / IDENTITY.md / USER.md 在 50 次请求里各出现 10 次。
- R2 的逐行扫描就是在这堆重复的大文本上进行的。

### R4 「按需求」视图和详情页存在 N+1 查询

- `_request_groups()` 对**每一条**匹配记录调用 `_activity_request()`（`:1031-1072`），每次调用内部还会再发多条查询（`:1322-1350`）。
- `_request_group()` 对当前页的每个分组再发 4 条以上查询（`:1074-1108`）。
- 每次打开详情（`record` / `raw`），都要重新执行 `_sync` 和 `_scope`（`:1650`、`:1832`）。

### R5 排行每次请求都从零计算

`capabilities()` 每次请求都新建临时表 `dc_capabilities`，再按类别分组统计（`:1183-1213`）。没有预先汇总好的结果表，也没有缓存。

### R6 旧版查看器：不分页、体积巨大、排序用不上索引、截断时不提示

- `collection_view.model_data()`（`agentpair/collection_view.py:68-93`）一次返回最多 250 条完整正文，实测 16.6 MB。
- AppLens 部分用 `ORDER BY json_extract(data,'$.timestamp')` 排序（`agentpair/devices.py:160`）。表的主键是 `(device_id, request_id)`（`:46`），没有时间列索引，所以要把这台设备每行约 290 KB 的 JSON 全部解析一遍才能排序。这就是 `summary=1` 只返回 340 KB 也要 18 秒的原因。
- 返回条数上限写死且不一致：AppLens 普通模式 50、摘要模式 200，SessionLens 200（`collection_view.py:80`）。截断时不提示，导致同一台设备在两种模式下显示的调用数不同（250 和 400）。

### R7 前端放大了问题

- 页面一打开就自动发起「所有设备 + 无筛选」的全局搜索。
- 前端超时设为 30 秒（`web_assets/data_center.js:229`），实际服务端 12 秒就失败了。
- 加载中没有骨架屏；同一条错误显示两遍；没有结果时分页按钮照样显示。
- 后端返回的 409 不区分「超时」和「锁忙」，前端也就没法给出不同的提示。

## 3. SessionLens 与 AppLens：数据链路、正确性与展示问题

### 3.1 数据链路

```
SessionLens（端侧读取 Codex / WorkBuddy 本地会话日志）
  └─ POST /api/sessionlens/events（platform.py:396-415；每批 ≤30 条，每条 ≤2MB，总请求 ≤4MB）
       └─ SessionStore.ingest（session_lens.py:85-）→ sessionlens.db：session_events(device, owner, id, session, event)
            + session_heads（每个会话的事件计数和摘要）
AppLens（端侧捕获 WorkBuddy 发给模型的请求）
  ├─ POST /api/applens/model-context（platform.py:417-424；每批 ≤3 个请求）
  │    └─ devices.ingest_model_context（devices.py:117-129）→ applens_model_context(device_id, request_id, data, received)
  │         + 同步执行凭据威胁扫描 credential_threats.scan
  ├─ POST /api/applens/llm/evidence → applens_llm_evidence   ← 数据中心不读取
  └─ POST /api/applens/otlp/v1/traces → applens_llm_spans   ← 数据中心不读取
数据中心（data-center.db）
  └─ 每次查询时 _sync() 把两边的增量投影成统一的 dc_records 和 dc_fields
       SessionLens → _session_projection：类型分为 user / tool_call / tool_result / reasoning / reply / context
       AppLens     → _app_projection：类型只有 context 或 http 两种；正文和拆出来的消息各存一份
旧查看器 /model-data/raw → collection_view.model_data：直接读两张源表，不经过 dc_*
```

### 3.2 数据正确性、完整性、去重

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| D1 | **不跨来源去重**：同一轮 WorkBuddy 对话，SessionLens 存一条「用户提问」，之后每次 AppLens 请求的上下文里又各带一份 | `DUPLICATES` 写了 `d.collector=r.collector` 条件，只在同一采集器内部、设备别名之间去重（`data_center.py:45-48`）；实测 50 次 AppLens 请求里有 218 条 user 消息 | 用 `collector=all` 搜一句提问，会同时命中 1 条 SessionLens 记录和 N 条 AppLens 记录；命中数和设备统计都偏大 |
| D2 | AppLens 的 Agent 被写死为 WorkBuddy | `data_center.py:823` 投影时 `source='workbuddy'`；`collection_view.py:72` 写死 `application='WorkBuddy'` | 现在 AppLens 只支持 WorkBuddy，所以数据暂时是对的；但筛选里「Agent=Codex + 采集来源=AppLens」永远为空，页面也没说明原因；以后接入其他应用会被错标 |
| D3 | AppLens 有两种来源（网络捕获 28 次，生成上下文 22 次），**可能是同一次调用被记了两份**（待核实） | 实测 `source` 分布；投影后都算作独立记录（`_app_projection`，`:647-649`） | 请求数可能被重复计算；页面没有区分两种来源的含义 |
| D4 | AppLens 有 3 条上报通道，数据中心只接入了 1 条 | 只同步 `applens_model_context`（`:803-823`）；`applens_llm_evidence` 和 `applens_llm_spans` 只有旧查看器的计数用到（`collection_view.py:38`） | 页面显示的「AppLens 覆盖」比实际采到的少，用户无从知道 |
| D5 | 时间口径不一致 | AppLens 记录了服务端接收时间（`received`）；SessionLens 只有源事件时间（`_sync` 写入时 `received=None`，`:800-802`；limitations 里也写明了） | 两种来源混在一起按时间排序，排序依据并不相同 |
| D6 | 排行只统计 SessionLens | `capabilities()` 只取 `r.kind='tool_call'` 的记录（`:1185-1193`），而 AppLens 记录的类型只有 context 和 http | 排行页让用户选「采集来源=AppLens」，结果永远为 0；AppLens 请求里的 tool_calls 没有计入排行 |
| D7 | 截断上限不一致且不提示 | 见 R6 | 同一台设备在两种模式下显示的调用数不同（250 和 400） |
| D8 | SessionLens 的事件冲突处理是对的，但页面看不到上传失败 | `ingest` 遇到重放冲突会抛错（`session_lens.py:104-105`）；`session_uploads` 表记录了失败原因，但数据中心不展示 | 数据缺了一段时，看不出是上传失败还是本来就没有 |

### 3.3 页面上两类数据的展示问题

1. **混排**：两种来源默认在同一个列表里按时间排序。但它们是不同性质的证据：一个是「Agent 做了什么」（SessionLens），一个是「发给模型的完整输入」（AppLens），而且粒度和体积差了 30 倍（平均 10.6 KB 对 290 KB）。
2. **筛选口径不一致**：
   - 「行为类型」里的工具调用、工具返回、已记录思路、Agent 回复，只对 SessionLens 有效；AppLens 只有「上下文记录 / 捕获的模型请求」。
   - 「内容位置」反过来，更适合 AppLens 那种拆开的消息。
   - 两类筛选同时出现，选了以后另一类数据就整体消失，页面不解释原因。
3. **命名混乱**：
   - 同一个概念在不同地方叫「采集来源 / 采集器 / collector」，另一个概念叫「Agent / 应用 / application / source」。
   - AppLens 在 `APPLENS_CLIENTS.md` 里又被说成「端侧应用分析器」（Windows / Android / macOS 客户端），和这里的「模型请求捕获」不是一回事。
   - 旧查看器的标题是「原始记录查看器」，新页面的标签是「按原始记录」，名字重复，但不是同一个功能。
4. **两套入口**：新版 `/model-data` 和旧版 `/model-data/raw` 并存，数据口径不同（旧版有条数上限，新版没有，但新版打不开）。

## 4. 整改意见（按影响排序）

### 后端

| 优先级 | 措施 | 预期效果 | 验收标准 |
|---|---|---|---|
| B1 | **把同步和统计从读请求里移走**：<br>• `_sync` 改由写入端触发或后台任务执行，读请求只读已提交的索引；<br>• `sources`、`facets`、各种计数、`capabilityRemaining` 改成预先汇总的统计表（按设备 × 采集器 × 应用 × 类型 × 天），写入时增量更新 | 消除约 12 秒的固定开销，默认页查询降到几十到几百毫秒 | 默认搜索 p95 ≤ 1.5s；`pageSize=1` 和 `pageSize=20` 耗时相差 ≤ 200ms |
| B2 | **去掉全局锁**：读请求不加锁（SQLite WAL 本身支持并发读），只对写入加锁；接口加上并发上限和排队上限 | 消除「锁忙也返回 409」 | 同时发 5 个默认搜索，全部 200，p95 ≤ 2s |
| B3 | **关键词搜索改用全文索引**：`dc_fields` 建 SQLite FTS5（trigram 分词，支持中文子串）；IP、域名保留结构化字段精确匹配，不再用 Python 函数 | 关键词搜索快 1–2 个数量级 | 搜 `password` 在全局范围 p95 ≤ 2s，并返回总数 |
| B4 | **AppLens 增量存储**：<br>• 每次请求只存「相比上一次请求新增的消息」，加上原始正文的哈希和对象存储引用；<br>• 不再把拆开的消息和完整正文各存一遍；<br>• SOUL.md 这类固定上下文按哈希只存一份 | 索引体积预计缩小 5–10 倍，与扫描量成正比 | 50 次请求的索引文本量 ≤ 现在的 20%；详情页仍能还原完整正文（由哈希校验） |
| B5 | **跨来源去重和关联**：SessionLens 的 user 记录与 AppLens 请求里的 user 消息按（设备、会话、规范化文本哈希）关联；结果计数提供「去重后」口径 | 命中数不再虚高，「按需求」视图能挂上对应的 AppLens 请求 | 同一句提问在全部来源中搜索，计为 1 个需求，并标明「AppLens 请求 ×N」 |
| B6 | **区分错误类型**：<br>• 超时返回 503 + `Retry-After`，提示文字说明原因；<br>• 锁忙或排队已满返回 429；<br>• 参数错误返回 400；<br>• 不再统一返回 409 加一句错误的「请缩小范围」 | 前端能给出正确提示 | 在三种场景下抓包，状态码和提示文字都与实际原因一致 |
| B7 | **默认查询加时间窗**：没有指定时间时默认最近 7 天；全局范围必须有时间上限；翻页改成按时间游标翻，不用 OFFSET | 默认查询的扫描量可控 | 第 1000 页和第 1 页耗时相差 ≤ 2 倍 |
| B8 | **旧查看器接口加分页**：`/api/audit/model-data` 默认只返回摘要，单页 ≤ 50 条，正文按单条按需加载；`applens_model_context` 加 `(device_id, received)` 索引并用它排序；超出上限时返回 `truncated` 和总数 | 19.6s / 16.6 MB 降到 1 秒以内、100 KB 以内 | 单设备首屏 ≤ 1s、≤ 200 KB；页面显示「共 N 条，已显示 M 条」 |
| B9 | **排行预先汇总**：写入时维护工具 / Skill / MCP 计数表；把 AppLens 请求里的 tool_calls 也算进去，或者明确声明只统计 SessionLens | 排行页秒开，口径清楚 | 排行首屏 ≤ 1s；选「采集来源=AppLens」时有数据，或显示明确说明 |
| B10 | **线上代码推送到仓库**，提供 `/api/version` | 修复可复测 | `/api/version` 返回的 commit 能在仓库里找到 |

## 5. 改版方案

### 5.1 页面定位与用户

- **用途**：按设备和时间，查看 AI Agent 实际做了什么（SessionLens），以及实际发给模型的内容（AppLens）。为「交互安全审计」的发现提供证据，也作为对外展示的样例。
- **用户**：
  - 主要用户：安全审计员和团队负责人，带着一个问题来查证据。
  - 次要用户：展示访客，想 10 秒内看懂平台采到了什么。

### 5.2 信息架构（改版后）

```
数据中心
├─ 范围栏：设备 · 时间（默认最近 24 小时）· Agent · 关键词/条件（保留现有语法和自动补全）
├─ 来源概览卡 ×2：SessionLens（会话日志）| AppLens（模型请求）
│     各自显示：条数 / 需求数或请求数 / 平均体积 / 最近时间 / 索引状态（复用 indexSync、unindexedRecords）
├─ 标签页
│  ├─ 会话（SessionLens，默认）：按需求分组（默认）或按原始记录；行为类型筛选；右侧显示本范围概况和常用工具
│  ├─ 模型请求（AppLens）：请求列表（时间、来源类型、目标、bodyBytes、bodySHA256）
│  │     → 详情：新增消息 / 上下文构成（system / SOUL.md 等 / user / assistant / tool）/ 完整正文（按需加载）
│  └─ 工具与能力排行（原 /model-data/rankings，并入此处）
└─ 记录详情抽屉：保留现有 5 个分区（概览、调用与结果、关联过程、上下文、原文依据）
```

### 5.3 功能处理清单：保留、合并、删除、调整

| 功能 | 处理 | 说明 |
|---|---|---|
| 关键词 / 条件查询、`kind=` 等自动补全、`&&` / `||` 语法 | **保留** | 这是核心能力；把「条件语法与示例」并入补全面板的帮助 |
| 「按需求 / 按原始记录」切换 | **保留**，放在会话页 | 「按需求」作为 SessionLens 的默认视图；AppLens 页不需要 |
| 记录详情抽屉的 5 个分区 | **保留** | 结构合理，只需改为按需加载 |
| 覆盖与已知缺口（limitations） | **保留，改为折叠** | 移到侧栏，平时只显示一行 |
| 「采集来源」下拉框 | **删除，改成标签页** | 两类数据性质不同，不应该混排 |
| 「原始记录查看器」`/model-data/raw` | **合并**到「模型请求（AppLens）」页 | 去掉两套入口，统一口径 |
| 「使用排行」独立页 | **合并**为第三个标签页 | 共用范围栏 |
| 能力类型、行为类型、内容位置三个下拉框 | **调整**：随所在标签页显示相应选项 | 会话页显示行为类型；AppLens 页显示消息角色和上下文类别 |
| 「查看最新记录」按钮 | **删除** | 默认就按时间倒序排列 |
| 表单错误提示和恢复条 | **合并**为一个错误状态组件 | 现在同一条错误显示两遍 |
| 「自然语言调查」（调用模型，需登录，会发送到第三方分析服务） | **移出**数据中心首屏，放到会话洞察或安全审计 | 访客用不了，还会产生费用，并且需要确认数据外发；放在搜索框旁边让人困惑 |
| 页脚免责声明 | **调整**：缩成一行，并入「覆盖与已知缺口」 | — |
| 「新增内容」差异列、上下文构成条 | **调整**（基于现有字段的新展示，示意稿里标注为「建议」） | 用现有 items 的 category 和 source 字段计算，不增加新的采集 |

### 5.4 SessionLens 视图（会话）

  - 需求原文；

### 5.5 AppLens 视图（模型请求）

## 6. 复测验收清单

1. 匿名打开 `/model-data` 和排行页：首屏 ≤ 1s 出现概览；默认搜索 p95 ≤ 1.5s；控制台 0 错误。
