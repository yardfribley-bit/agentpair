# AgentPair 设计文档

版本：0.1（设计草案）

日期：2026-09-29

状态：离线修复状态机、双节点真实角色调用、多轮任务平台及动态角色画布已实现。已完成两轮有历史承接的真实代码建议与复核。隔离代码执行、真实测试驱动的自动修复仍待实现。

## 1. 目标与边界

### 2026-09-29 平台交互范围补充

用户应通过 Navigator Web 发布新任务，而不是修改固定脚本中的目标。Web 入口向核心提交 TaskSpec；任务类型选择已注册的 TaskAdapter（网站分析为第一个示例），不允许客户端提交可在主机上直接执行的命令。核心维护任务队列、角色协作、状态、事件、预算与停止条件；两个云节点执行任务，用户查看过程、补充约束、取消及导出结果。

新增需求采用“表单 → 队列 → Navigator 规划 → Driver 执行 → Navigator 复核 → 补查或结束”的统一生命周期。验收条件按适配器定义，未知与失败不得渲染成成功。补充要求须形成版本化消息，影响后续轮次而非伪造已完成步骤；取消须停止后续调用并说明在途调用不能保证即时中断。

用户的任务发布与云资源创建是两个独立授权，不因提交任务自动扩容或延长租期。可写入口现已实现登录、Origin与CSRF检查及消息限制，仅监听Navigator loopback，通过SSH通道访问。公网只读页面展示编程实跑快照；两者不是同一个授权入口。任务与预算保存于SQLite，用户消息启动下一轮，阶段事件驱动双角色画布。企业AgentReins审计不在当前范围。自主工具规划、自动补查及隔离执行仍待实现，当前网站适配器调用固定取证工具。

AgentPair 是一个可运行、可观察、任务可替换的双 Agent 结对编程范例。

核心问题不是让两个模型同时回答，而是让它们围绕真实代码与测试结果协作：一个规划方向，一个实现代码，失败后修复实现或更换方案。

第一版目标：

- 从结构化任务描述生成 Python 代码。
- 由更强的 Navigator 规划，由低成本且具备编码能力的 Driver 实现。
- 执行真实、不可被模型修改的验收测试。
- 完成至少一条规划、编码、测试、反馈的闭环，支持有限轮次迭代。
- 保存可重放的方案、代码、测试结果、模型用量和停止原因。

第一版不做：云资源弹性调度、复杂队列、多人项目管理、生产仓库自动提交、企业审计管理端改造、任意 Shell 工具、自行安装依赖、任意网络访问。

AgentReins 数据分析是后续示例任务，不是框架核心。已有执行分析脚本保留为独立原型，不将“分析员＋复核员”误称为完整结对编程引擎。

## 2. 参考与差异

参考用户提供的 PairCoder 论文：*A Pair Programming Framework for Code Generation via Multi-Plan Exploration and Feedback-Driven Refinement*，ASE 2024，DOI `10.1145/3691620.3695506`。

采用其 Navigator–Driver 分工、多方案探索、真实执行反馈和重复失败时换方案的核心思想。第一版简化为两个候选方案、最多三轮编码与测试，不实现 embedding 聚类、多批采样，也不声称复现论文实验或获得同等性能。

规划说明只要求简短方案、约束、取舍和修复理由；不要求或保存模型隐藏思维链。

## 3. 角色与责任

| 组件 | 责任 | 不允许承担的职责 |
|---|---|---|
| Navigator Agent | 理解任务、比较候选方案、选方案、解释失败、指示修复或换方案 | 宣布未经执行的测试通过；修改验收标准 |
| Driver Agent | 按方案生成候选代码，按修复指令修改 | 直接执行任意命令；修改测试；决定任务完成 |
| Executor | 隔离执行候选代码，返回真实测试反馈 | 调用模型；修改代码；把模型描述当作执行记录 |
| Coordinator | 校验协议、管理状态、转发上下文、保存产物、控制预算与轮数 | 充当第三个规划 Agent；绕过失败结果强行标记成功 |

Agent 是独立角色、独立提示与上下文，不要求物理上各占一台机器。第一版允许同一协调进程顺序调用两个角色；后续可将模型调用工作节点拆到两台 Linux，协议不变。

## 4. 模型分配

Navigator 优先选理解约束、方案判断和故障诊断能力较强的模型。Driver 优先选具备可靠代码生成能力的低成本模型。两个角色可使用不同模型、同一模型的独立会话或不同供应商。

模型 ID、API 地址、认证引用、上下文限制和计费资料均属于配置，不硬编码品牌排名。中转服务声明的模型名称只记录为供应商返回值，不视为底层模型身份的独立证明。

第一版不自动升级模型。升级需要新的调用成本估算及用户批准。后续用相同任务和测试比较“强规划＋低成本编码”与“两边低成本”，按成功率、修复轮数、耗时和总费用评估，而非只比较输出文风。

## 5. 最小执行流程

```text
任务与固定测试
      ↓
Navigator：提出两个候选方案并选择一个
      ↓
Driver：生成候选代码
      ↓
Executor：真实执行测试
      ├─ 通过 → 保存结果 → tested_pass
      └─ 失败 → 检查上限和重复 → Navigator：修复或换方案
                                         ↓
                                     Driver：修改
                                         ↓
                                      再次测试
```

执行规则：

1. 先校验任务、固定测试、运行环境和费用配置，未通过不得调用模型。
2. Navigator 一次返回两个不同候选方案、选中方案和简短选择理由。
3. Driver 返回完整的单文件 Python 代码；第一版不采用跨文件补丁或自动依赖安装。
4. Coordinator 校验输出大小和结构，保存候选版本，交给 Executor。
5. Executor 返回 `pass`、`wrong_answer`、`runtime_error` 或 `timeout`。无法启动执行器属于基础设施错误，不能归为候选代码错误。
6. 失败后，Navigator 根据代码和真实反馈选择 `repair` 或 `switch_plan`。
7. 重复代码或重复的结构化失败签名触发换方案；用过的方案不再选。没有剩余方案时停止。
8. 测试通过或达到轮数、时间、费用限制后停止。失败也交付最后一个候选版本，但明确标注未通过。

最多三轮编码与测试，正常路径最多六次模型请求（首次规划、首次编码，之后每轮决策与编码）。任何额外请求都计入请求上限；第一版遇到无效 JSON 不自动追加修复请求。

代码重复依据完整代码 SHA-256。失败签名采用错误类别、失败测试 ID、实际/期望值摘要或标准化异常类型，不包含耗时、随机临时路径等易变化字段。

换方案后清空该方案的重复检测历史，但保留整次运行的审计记录，并向 Navigator 提供已尝试方案及失败摘要，避免循环返回旧方案。

## 6. 任务与消息协议

### 6.1 任务 TaskSpec

```json
{
  "protocolVersion": 1,
  "taskID": "demo-deduplicate-v1",
  "description": "实现整数数组的稳定去重，保留首次出现顺序",
  "language": "python",
  "entrypoint": "solve",
  "inputContract": "JSON integer array",
  "outputContract": "JSON integer array",
  "constraints": ["只使用标准库", "不得修改输入"],
  "visibleTests": [{"id": "t1", "input": [2, 1, 2], "expected": [2, 1]}],
  "testSuiteRef": "demo-deduplicate-v1-fixed",
  "limits": {"maxRounds": 3, "maxPlans": 2, "maxRequests": 6}
}
```

固定测试由程序维护，`testSuiteRef` 解析为受信任配置，不接受模型返回的路径。模型可看到公开测试，但不得修改测试文件；保留测试不进入模型上下文，作为额外验收，结果与公开测试分别记录。

### 6.2 Navigator 输出

首次：`plans[{planID, title, steps, risks}]`、`selectedPlanID`、`reason`。

后续：`decision`（repair/switch_plan）、`planID`、`repairInstructions`、`reason`。

方案 ID 必须存在且可用。Navigator 不具备 `success` 决策，只有 Executor 有权产生测试通过记录。

### 6.3 Driver 输出

`{planID, code, changeSummary}`，其中 `code` 是 UTF-8 源码字符串，而不是 Markdown 代码块、执行命令或文件系统路径。代码只能映射到协调器指定的 `candidate.py`。

### 6.4 TestFeedback

`{candidateHash, suiteHash, status, passedCount, totalCount, failures, durationMs, stdoutTruncated, stderrTruncated}`。

失败记录含测试 ID、错误类别、实际/期望值或异常摘要。退出码和运行日志由 Executor 捕获，不接收模型自报。至少一个固定测试实际执行，且全部通过，才能返回 `pass`。

### 6.5 通用消息封装

每条消息含 `protocolVersion`、`runID`、`messageID`、`round`、`role`、`parentMessageID`、`payload`、时间和模型调用记录。结果与运行、轮数和代码版本绑定，拒绝旧轮结果或其他任务的消息。

## 7. 上下文管理

Navigator 接收需求、约束、公开测试、候选方案、当前代码和结构化反馈。Driver 接收需求、当前方案、当前代码及修复指令。

不把整次聊天记录无限追加。历史只保留有用摘要和最近失败；原始消息保存在本地运行记录中。超过上下文上限时先缩减历史，仍超过则明确停止，不静默截断需求、测试或关键代码。

任务描述、文件、日志和另一个 Agent 的输出都是待处理数据，不得覆盖角色规则。模型不拥有云厂商密钥、企业审计管理员密码、运行器宿主权限或任意工具权限。

## 8. 执行隔离

模型生成的代码是不可信代码。不得在用户 Mac 主进程中直接 `exec`，也不得将云节点本身当作充分隔离。

第一版执行器优先使用 Linux 容器：非 root 用户、禁网、只读根文件系统、移除 capabilities、禁止提权、限制 CPU/内存/进程数/执行时间。代码和固定测试只读挂载，临时写入只允许受限 tmpfs。不挂载 Docker socket、用户主目录、SSH 私钥或模型凭据。

协调器及模型 API 调用在容器外，执行容器不继承它们的环境变量。容器运行时需另设日志大小上限；宿主 watchdog 杀死超时容器及其子进程。

第一版任务限定为标准库纯函数 `solve(payload)`，输入输出是 JSON。禁止生成代码修改宿主路径、测试、运行协议或外部状态。文件操作和联网任务以后另立执行策略。

容器隔离并非绝对安全。运行环境不满足上述策略时失败关闭，提示缺少条件，不能自动降级为宿主裸跑。对生产数据的任务需另外批准访问与传输范围。

## 9. 成本、时间与终止

费用分开记录：模型调用、云实例、磁盘、公网。第一版本地执行不自动购买云资源。

模型调用前根据供应商实际价格和输入/输出上限估算费用，预留下一请求的最坏费用；估算后超过剩余预算则停止。输出 token 上限、请求数上限和运行截止时间必须同时生效。

缺失真实计费资料时不能宣称已实施人民币硬上限。单次历史账单可用于估算，但不是输入/输出单价，更不保证未来价格不变。要提供严格金额上限，需供应商侧实验令牌硬额度或可验证的计费与限额能力；否则运行标记为 `estimated_budget`，由用户选择是否接受。

模型超时可能已经收费，第一版不自动重试。记录 `billing_unknown`，停止本次运行。无 usage 或价格缺失时费用为 unknown，不填零。

终态：

| 状态 | 含义 |
|---|---|
| `tested_pass` | 固定测试通过，不能扩大为任意输入下必然正确 |
| `tests_failed` | 轮数用尽仍未通过 |
| `plans_exhausted` | 无可用方案 |
| `budget_exhausted` | 不足以安全发起下一请求 |
| `deadline_exceeded` | 超过运行截止时间 |
| `protocol_error` | 模型输出或消息状态不合法 |
| `infrastructure_error` | API/运行器异常，结果不能归因于代码 |
| `cancelled` | 用户取消，停止新调用并终止执行器 |

云版本必须先建立独立清理机制，再创建资源。停机不等于停止所有费用；清理需逐项核对实例、云盘、公网 IP 与账单。本项目此前仅验证过单台 UCloud 创建、启动和删除，尚无已验证的一小时自动清理系统。

## 10. 产物与可观察性

```text
runs/<runID>/
  manifest.json          # 状态、配置摘要、截止时间、环境版本
  task.json              # 任务定义，不含认证信息
  plans.json             # 候选方案和选择
  messages.jsonl         # 角色交互和调用用量
  rounds/01/
    candidate.py
    feedback.json
  result.json            # 最终状态、候选哈希、测试和费用摘要
```

运行目录默认私密并忽略版本控制。模型凭据只通过运行时安全配置注入，不写入任务、消息或错误日志。文件写入使用原子替换；清单与内容哈希保留关联。日志需要脱敏，不能把异常请求头或环境变量原样输出。

最小可观察指标：方案切换、每轮代码变化、测试通过比例、停止原因、角色耗时、token 用量、实际或估算费用。报告保留“未取得 usage”“计费待核对”等缺口。

第一版保存足够记录用于人工复盘，不实现中断恢复。以后恢复必须先核对不确定请求是否已经收费、代码是否已经执行，避免重放造成重复支出或副作用。

## 11. 模块划分与实施顺序

建议模块：`contracts`（协议）、`model_client`（调用和计费）、`navigator`、`driver`、`executor`（隔离测试）、`coordinator`（状态机）、`run_store`（产物）。不把业务任务硬编码在角色内。

1. **协议与离线状态机**：用确定性假模型验证正常通过、修复、换方案和停止路径，不计费。
2. **隔离执行器**：验证真实候选代码、固定测试、超时、输出限制和隔离失效时拒绝运行。
3. **真实双模型演示**：一个无私密数据的小任务，完整保存规划、代码和测试结果；不宣称假模型结果是真实模型协作。
4. **云部署验证**：程序不变，部署至两台短时 Linux，分别承载两个角色，协调器转发；任务完成后清理。
5. **可替换任务接入**：增加工程任务或 AgentReins 脱敏分析示例，再考虑队列和弹性。

## 12. 验收标准

- 真实演示至少一次 Navigator 规划、Driver 编码、Executor 实际测试；最终产物能独立重跑。
- 失败修复、重复失败换方案、方案耗尽、轮数上限、费用上限、取消和基础设施异常有自动测试。
- 通过标记必须对应相同 candidateHash 和 suiteHash 的真实完整测试结果。
- 测试不可被 Driver 修改；隐藏测试不进入模型上下文。
- 执行容器不能访问网络、凭据和宿主文件，超时不会遗留子进程或容器。
- 产物不含密钥；费用缺失不伪造；未通过不报成功。
- 两台云机不是本地最小闭环的前置条件，云部署成功也不能代替结对编程成功。

当前代码与本设计的差距：已有分析辅助原型、协议与协调状态机及离线测试；真实编码角色、人民币预算控制、产物持久化和隔离执行器尚未完成。离线范例只产生 `simulated_pass`，不表示真实生成代码已通过测试。
